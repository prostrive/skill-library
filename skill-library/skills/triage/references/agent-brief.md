# Writing an agent brief

An agent brief is the comment that makes a ticket ready to build. The ticket body and the discussion are background. The brief is the contract.

## Rules

- **Describe behavior, not steps.** Say what the system does when the work is done. Let the builder choose how.
- **Stay valid for weeks.** Name types, function signatures, config shapes and contracts. Do not name file paths or line numbers. They change.
- **Make every criterion testable on its own.** "The list shows the newest item first" is testable. "Sorting works" is not.
- **Say what is out of scope.** That stops the builder from widening the work.
- **Use the project's words** from `GLOSSARY.md`.
- **Write down the dev's decisions** from triage. Do not add your own.

## Template

```markdown
Generated by AI during triage.

## Agent brief

**Type:** bug / feature
**Summary:** one line

**Now:** what happens today. For a bug, the broken behavior and the reproduction result.

**Wanted:** what happens after the work. Include edge cases and error cases.

**Key interfaces:**
- `TypeName`: what changes
- `functionName()`: what it returns now and what it returns after

**Acceptance criteria:**
- [ ] criterion 1
- [ ] criterion 2

**Out of scope:**
- what this ticket does not change
```

## A weak brief

```markdown
Fix the filter bug. It is around line 150 of the list handler.
```

It has no type, no current or wanted behavior, a line number that will go stale, no criteria and no scope.
